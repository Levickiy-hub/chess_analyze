# Stockfish и массовый анализ

## Подтверждённый контракт

Приложение использует @se-oss/stockfish 1.0.1, который запускает node с bundled stockfish-17.1-8e4d048.cjs и WASM 78 868 653 B (dist/index.js:23–24). Подтверждено `id name Stockfish 17.1 WASM Multithreaded`. Не native stockfish.exe. Реализованный протокол: uci, ожидание готовности wrapper.waitReady, setoption MultiPV, position fen, go depth, info cp/mate/PV, bestmove. Собственный код только инициирует new Stockfish, waitReady и analyze(fen,depth), сохраняет bestmove и первую score строкой. PV, nodes, depth, nps/time доступны из wrapper и теряются.

| Параметр / способность | Текущее состояние |
|---|---|
| depth | config DEPTH=12; вызов analyzer:71 |
| число процессов | config POOL_SIZE=16; init последовательно запускает все |
| Threads / Hash | Приложение не задаёт; engine объявил defaults 1 и 16 MiB; проверка аудита явно выставила 1/16 |
| movetime / nodes / общий timeout | Не заданы и не доступны из app config |
| MultiPV | wrapper default=1; приложение не предоставляет альтернатив |
| WDL | Не включён UCI_ShowWDL, не сохраняется |
| PV / ponder | Возвращаются wrapper, app отбрасывает |
| engine build / NNUE / параметры / timestamp | Не сохраняются с результатом |
| Syzygy | Не конфигурируется, интеграции/tablebases нет |
| ucinewgame / история повторений | App отправляет только FEN каждой позиции, явного reset и moves history нет |
| ошибка / timeout / restart | Собственных обработчиков error/exit и watchdog нет |
| quit/terminate | wrapper.terminate существует; app close не вызывает его |

Smoke: один экземпляр, три позиции depth=4, Threads=1 Hash=16; bestmove g1f3, cp39, PV и 512 nodes на старте. Время поиска трёх позиций 18 ms в последнем запуске, **без времени инициализации**; весь диагностический процесс примерно 5.5 s. Это не benchmark depth12 и не основание экстраполировать партии в секунду. Процесс аудита завершён прямым terminate в finally; пул приложения не запускался.

## Алгоритм и проблемы

analyzeGame acquires engine на всю партию, loadPgn/history, строит новую стандартную доску и на каждом полуходе ищет pre-позицию. На P полуходов — P engine calls. Затем второй проход сравнивает соседние оценки; post последнего хода не рассчитывается. Нормализация к POV белых отсутствует; loss, категории и графики недостоверны (контрпример в ANALYTICS_AUDIT.md). Mate строки сохраняются, но getCategory для них недостижим. Первый/последний режимы, критические позиции, глубокий повторный анализ, позиционный кэш и search limits отсутствуют.

Возврат движка выполнен в finally analyzer:151–153 — полезное решение. Но Promise.all в main:70 отвергается при первой ошибке, нет try/finally main и per-job status. Другие уже созданные Promise могут продолжать поиск, результат не сохраняется. init при ошибке посередине не завершает ранее поднятые процессы. main().catch(console.error) не задаёт exitCode. В close:43–46 очищаются массивы, а не дочерние процессы: проверено fake-engine terminateCalls=0. Не вызванные resolve из waiting при закрытии могут остаться незавершёнными.

## Очередь и параллелизм

Это FIFO callback очередь в RAM, не фоновые задания с идентификаторами. .map вызывает analyzeGame сразу для всех партий; acquire ограничивает **одновременные игры** до числа engines, но заранее создаются Promise и ожидания для всей выборки. Нет приоритета, дедупликации, durable job, lease, cancel/pause/resume, retry/backoff, recovery, heartbeat. MAX_GAMES — первые N текущего массива; выборки по ID/period/status нет. Прогресс console completed/total и ply/game; отдельно ошибок/остатка/обработанных не хранится. Анализ повторно запускается для всего массива независимо от прошлых результатов. Запись только после полного Promise.all.

Wrapper inspected only at integration boundary: stdout data chunk делится split('\n') без явного переноса незавершённого хвоста (dist/index.js:25–33); это риск потерять разбитую UCI строку, не воспроизведённый дефект. info может перезаписываться неполной строкой с default score; нужен regression на реальном stream. Его встроенный StockfishPool также существует, но автоматически менять на него свой пул без проверки контрактов нельзя. Error EventEmitter требует явной обработки в приложении.

## Ресурсы и расчёт масштаба

Не выполнялся анализ даже одной полной реальной партии. Исходные предположения для сценария: P=30607/390=78.48 полухода/партию из локального набора; среднее время одного поиска depth12 неизвестно, рассматриваем **условно 0.1–1 s**; эффективный parallelism=4 только для расчёта. T≈N*P*t/4 без I/O/инициализации/конкуренции CPU. Одновременных процессов сейчас фактически настроено 16, это не означает 16-кратное ускорение. Для конечной политики CPU учитывать reserve cores, Threads и memory budget; 16*16=256 MiB только Hash, плюс WASM/heap/дочерние Node, реальный RSS не измерялся.

| Объём | Примерно engine calls | Условное время при 0.1–1s и 4 workers | Raw при текущих 3.89kB/игру | Весь analysis при 133.5kB/игру | Архитектурная оценка |
|---|---:|---|---:|---:|---|
| 1 000 | 78 480 | 0.55–5.45 h | 3.89 MB | 133.5 MB | Вычислимо при ресурсах, но recovery и корректность не обеспечены |
| 10 000 | 784 800 | 5.45–54.5 h | 38.9 MB | 1.34 GB | Full-memory Promise/results, JSON и повторный анализ становятся значительным риском |
| 50 000 | 3 924 000 | 27.25–272.5 h | 194.4 MB | 6.67 GB | Требуется потоковая обработка и persistent queue/storage |
| 100 000 | 7 848 000 | 54.5–545 h | 388.8 MB | 13.35 GB | Текущая архитектура не подтверждена и эксплуатационно непригодна |

Объёмы десятичные; HTML/JSON повторения как в текущем месяце, без сжатия, кэша и сохранения новых PV. Состав будущих партий может существенно изменить оценки. Это сценарные расчёты, не результаты нагрузки и не сроки разработки. Отдельный analysis.json около 29.1kB/игру; весь analysis многократно дублирует данные. Лимиты V8 на строки/heap делают один массив и JSON.stringify на 100k неприемлемой ставкой без измерений. Сортировка allMoves O(M log M) только ради top5 избыточна; потоковый top-k снизит память/CPU. PGN parsing, JSON.stringify, SVG/HTML конкатенация и sort синхронно блокируют event loop, engine процессы вычисляют отдельно.

## Необходимые изменения

B01/B03 — корректный POV/пост-позиции/начальный FEN, B04/B07 — управляемый engine adapter с таймаутом/error/restart/stop/terminate, B05/B08 — per-game checkpoint и leases, B27 — измерения depth12 на заранее согласованной малой выборке. Ключ position cache включает engine build, options, search budget, POV/score schema и достаточное состояние позиции/повторений. Режимы quick/standard/deep хранить как версионированные presets; нельзя молча смешивать их в трендах. Промежуточные результаты фиксировать транзакционно по партии/позиции, статистику считать независимо от повторного Stockfish.
