# Комплексный аудит проекта персональной шахматной аналитики

## 1. Контекст проекта

В репозитории находится ранее начатый, но не завершённый проект приложения для персональной шахматной аналитики на основе истории партий Chess.com.

Конечная цель проекта — создание полноценной аналитической системы, которая позволяет:

- Получать всю доступную историю партий пользователя Chess.com.
- Хранить партии и связанные с ними данные.
- Автоматически анализировать все партии с помощью Stockfish.
- Анализировать каждый ход игрока и его соперников.
- Формировать комплексную статистику за произвольный период.
- Выявлять систематические ошибки, сильные и слабые стороны игрока.
- Анализировать дебютный репертуар, миттельшпиль и эндшпили.
- Анализировать управление временем и игровые сессии.
- Генерировать персональные рекомендации.
- Создавать тренировочные задачи на основе собственных ошибок пользователя.
- Отслеживать изменение шахматных навыков и прогресс игрока.

Приложение должно представлять собой не просто аналог анализа отдельной партии Chess.com Game Review, а систему комплексного анализа всей игровой истории пользователя.

## 3. Ограничения проведения аудита

На этапе аудита:

- Не изменяй исходный код приложения.
- Не выполняй рефакторинг.
- Не устанавливай новые зависимости без согласования.
- Не изменяй существующую архитектуру.
- Не удаляй файлы.
- Не изменяй структуру базы данных.
- Не применяй миграции к существующим базам данных.
- Не изменяй конфигурационные файлы.
- Не удаляй существующие данные.
- Не выполняй ресурсоёмкий массовый анализ партий.
- Не запускай операции, способные повлиять на рабочую среду.
- Не раскрывай пароли, токены и другие секреты из конфигурационных файлов.
- Не считай функциональность реализованной только на основании её упоминания в документации, названия файла или наличия элемента интерфейса.

Допускается:

- Чтение исходного кода.
- Изучение структуры репозитория.
- Анализ конфигураций.
- Изучение Git-истории.
- Поиск использования компонентов и функций.
- Изучение схем базы данных и миграций.
- Выполнение безопасных диагностических команд.
- Запуск существующих тестов в безопасной среде.
- Проверка сборки без изменения исходного кода и зависимостей.
- Проверка приложения в изолированной локальной среде, если это безопасно.
- Создание отдельной документации по результатам аудита.

Если выполнить какую-либо проверку невозможно, зафиксируй причину и не выдавай предположение за подтверждённый результат.

## 14. Правила оценки функциональности

Для каждого требования используй один из статусов:

- **IMPLEMENTED** — реализовано полностью, работоспособность подтверждена.
- **IMPLEMENTED_UNVERIFIED** — реализация существует, но работоспособность не подтверждена запуском или тестами.
- **PARTIAL** — реализована часть необходимой функциональности.
- **FRONTEND_ONLY** — реализован только пользовательский интерфейс.
- **BACKEND_ONLY** — реализована только серверная логика.
- **MOCK** — используются статические, тестовые или демонстрационные данные.
- **BROKEN** — реализация существует, но обнаружена неисправность.
- **NOT_IMPLEMENTED** — реализация отсутствует.
- **UNKNOWN** — недостаточно информации для определения состояния.
- **NOT_APPLICABLE** — требование неприменимо, с обязательным обоснованием.

Для каждого требования указывай:

- Уникальный идентификатор.
- Название модуля.
- Название требования.
- Статус.
- Приоритет.
- Описание существующей реализации.
- Подтверждающие файлы.
- Конкретные функции, классы или компоненты.
- Номера строк, где это возможно.
- Способ проверки.
- Обнаруженные проблемы.
- Недостающую функциональность.
- Рекомендуемое действие.
- Зависимости от других требований.
- Оценку сложности реализации.

Используй следующие приоритеты:

- **P0** — критически необходимая базовая функциональность.
- **P1** — основная аналитическая функциональность.
- **P2** — расширенная аналитика и тренировки.
- **P3** — дополнительные возможности и дальнейшее развитие.

Используй следующую относительную оценку сложности:

- **XS** — минимальное изменение.
- **S** — небольшая доработка.
- **M** — полноценная функциональная задача.
- **L** — крупный модуль.
- **XL** — сложная подсистема.

Не используй сроки разработки без достаточных исходных данных.
