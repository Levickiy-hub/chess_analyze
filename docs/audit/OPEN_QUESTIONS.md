# Вопросы перед разработкой

Ответы ниже нельзя достоверно получить из поставленных файлов. Значения USERNAME/DEPTH/POOL_SIZE и существование конкретных экранов сюда не включены: они уже установлены. Рекомендуемые варианты — рабочие предложения, не разрешение на изменение среды.

| ID / категория | Неизвестное решение | Варианты и компромиссы | Рекомендация / что разблокирует |
|---|---|---|---|
| Q01 Архитектура | Продукт остаётся личным локальным или нужен сервер с несколькими владельцами? | Local: простая установка/SQLite/приватность, нет удалённого общего доступа; server: auth/PostgreSQL/operations сложнее, доступ с устройств | Начать с local-first, но owner/profile IDs заложить; решение до B05/B10 |
| Q02 Архитектура | Какие rules нужно реально поддерживать? | Только standard: минимальная цена и проверяемость; Chess960/variants: отдельные правила/движки/UI | Standard явно фильтровать, raw остальных сохранять; расширять по реальным партиям |
| Q03 Функциональность | Должен ли интерфейс позволять произвольные публичные профили и ручной PGN импорт? | Только свои profiles: проще доступ/объём; любые: удобнее сравнения, больше лимитов/privacy и untrusted input | Несколько явно добавленных profiles одного owner; импорт PGN отдельным сценарием после escaping |
| Q04 Функциональность | Какой уровень auto-sync и auto-analysis нужен? | Ручной: предсказуемые ресурсы; расписание: актуальность, scheduler и resource window; постоянный worker: удобство, расход CPU | Сначала manual jobs, затем opt-in расписание с бюджетом; B06/B08 |
| Q05 Методология | Что пользователь будет называть «точностью»? | Engine agreement: прозрачно, не Chess.com; expected-score loss: содержательнее, требует калибровки; копирование закрытой Chess.com методики: нет гарантии эквивалентности | Сохранять agreement отдельно, проектировать свою named accuracy с формулой и version; B09 |
| Q06 Методология | Какие минимальные N и критерии значимости нужны для рекомендаций? | Фиксированный N: просто, грубо; интервалы/модель: точнее, сложнее; всегда показывать: риск неверных выводов | N+coverage+confidence и запрет категоричных советов при малом N; согласовать на pilot data |
| Q07 Методология | Насколько сложными должны быть объяснения мотивов/стадий/навыков? | Детерминированные эвристики: объяснимы, ограничены; annotated ML/LLM: гибче, требует данных/валидации/privacy | Rule-based evidence first, LLM только дополнительное изложение проверенных фактов |
| Q08 Инфраструктура | Какая машина и допустимый CPU/RAM/время анализа? | Desktop interactive budget: меньше workers, дольше; dedicated host: быстрее, эксплуатация/стоимость; native engine: потенциально эффективнее, нужна проверка | Измерить depth12 на малой разрешённой выборке, зарезервировать ресурсы; не считать pool16 оптимальным |
| Q09 Инфраструктура | Где официальный Git remote/история и ожидаемая среда поставки? | Восстановить существующий remote: сохраняет историю; новый repo: просто, история потеряна; контейнер: воспроизводимость, дополнительный runtime | Найти оригинальный репозиторий до настройки CI; без этого аудит ограничен файловым snapshot |
| Q10 Инфраструктура | Что задаёт небезопасную TLS политику runtime? | User/system env, оболочка или launcher: разные места исправления; причина в repo не найдена | Проверить владельцем среды перед реальным sync; не менять глобальные env в аудите |
| Q11 Инфраструктура | Нужны ли локальные Syzygy и какой объём/сеть допустимы? | Local: offline, большой диск; remote: меньше установка, latency/privacy; без TB: heuristics, нет теоретической гарантии | Optional adapter с явным coverage; выбрать после corpus/endgame потребности |
| Q12 Интерфейс | Browser app, desktop shell или только улучшенные HTML отчёты? | HTML export: мало зависимостей, ограниченная интерактивность; localhost web: полноценный review, сервер; desktop shell: упаковка сложнее | Local web UI + сохранить статический export; framework выбрать отдельно |
| Q13 Интерфейс | Какой пользовательский timezone и поведение period/session filters? | Europe/Moscow текущей среды: удобно сейчас; per-profile IANA setting: переносимо; UTC only: проще, менее удобно | UTC storage и configurable IANA timezone; текущий Europe/Moscow как начальный UI выбор, не жёсткая бизнес-логика |
| Q14 Организация | Какие данные можно публиковать/передавать optional AI и как распространять engine? | Полностью локально: приватнее; публикация/облако: удобство, условия данных/согласие; bundled GPL engine vs внешняя установка: разные обязательства упаковки | Локальный режим до явного решения, separate license notices/source obligations до релиза |
| Q15 Организация | Какая первая полезная версия и критерий принятия проекта? | Полная история+review: быстрый фундамент; сразу все skill/recommendation/training: большая неопределённость; только batch CLI: меньше UI ценности | Первая версия после этапов 0–6, с корректным импортом/анализом/review/базовыми трендами; затем расширения |

Эти вопросы не блокируют сам аудит и не требуют повторно подтверждать уже разрешённое чтение/документирование. Разработку сейчас не начинать. Главные решения перед ней: Q01 (модель установки), Q05 (методика), Q08 (ресурсы), Q09 (репозиторий), Q10 (TLS).
